# Version 1 contract

Collection declares a choice; it never proves identity or grants permission. Origin checks constrain browser use, not non-browser attackers. Public site IDs are public configuration.

Base API URL excludes `/v1` (e.g. http://127.0.0.1:4310). Browser requests use credentials: omit. Origin must exactly match an allowed origin of the configured site. HTTPS origins only, except localhost/127.0.0.1 development. CORS explicit origins, Vary: Origin, no cookies, allow Authorization, Content-Type, X-Agent-Site, GET/POST/DELETE/OPTIONS. All responses Cache-Control:no-store; body max 8KiB. JSON requests require application/json.

- POST /v1/sessions JSON `{siteId, bindingContext?}` ->201 CreatedSession (src/protocol.ts). sessionToken opaque random256bit, stored only hashed server-side. Anonymous sessions valid30minutes. Optional bindingContext minted by customer's server, signed with its per-site secret. Tokens never in URLs/logs.
- GET /v1/sessions/current ->200 SessionStatus, headers Authorization:Bearer sessionToken, X-Agent-Site:siteId. Exact site/origin/token/expiry/revocation verification.
- POST /v1/declarations JSON `{choice,requestId,agent?}` with same headers ->200 RecordedDeclaration. requestId UUID, idempotent per session; same key with different choice ->409. Optional `agent` `{name?,provider?,purpose?}` is the agent's own description: each field is trimmed text of at most 100 characters without control characters, empty or missing means unknown, and anything else ->400. It is kept from the first accepted request, so a retry can't change it. One final choice per session; different new choice after acceptance ->409. Site and origin from bound server session, never body. Choice any of ai_assistant/person/prefer_not_to_say.
- DELETE /v1/sessions/current ->204 invalidates session token. Evidence retained for retention period. Idempotent on already closed token, not unknown/wrong site/origin. reset() invalidates then starts a new session.
- GET /v1/events?siteId=...&limit=100 -> JSON `{events:[{id,siteId,origin,sessionId,choice,evidence,createdAt}]}`. Authorization:Bearer site's secret, server-to-server only (no CORS). Limit1–1000; newest first. No token/bindingContext/bindingHash/private secret fields.
- POST /v1/verify JSON `{siteId,origin,sessionBinding,receipt}` -> `{valid:true,sessionId,eventId,choice,evidence:"self_reported"}`. Server-to-server only, no CORS, Authorization:Bearer site's secret. Host supplies its actual active session binding. Checks signed claims and the stored declaration, expiry and revocation. Public helper `verifyDeclarationOnline(receipt,{apiUrl,siteId,origin,secret,sessionBinding,now?,fetch?})` fails closed. Offline `verifyDeclaration` only verifies signed claims and cannot observe subsequent revocation.
- Owner API: server-to-server only (no CORS; a request with an Origin header ->403), for the dashboard's server. Authorization:Bearer the customer's Supabase access token, verified locally against the project's published keys. GET /v1/owner/products -> `{products,deleted}`: `products` each with its `environments`, production first, and `deleted` the owner's deleted products that can still be restored, `{id,name,deletedAt,restorableUntil}`, most recently deleted first. POST /v1/owner/products JSON `{name,origins}` ->201 `{product,serverSecret}` creates the product and its production environment; this is the only time that secret is returned. GET or PATCH (JSON `{name}`) /v1/owner/products/:id -> `{product}`. DELETE /v1/owner/products/:id ->204 deletes the product: every other route then treats it as missing, and its sites stop answering within the 30-second site cache, but nothing is removed yet. POST /v1/owner/products/:id/restore -> `{product}` brings it back with the same site IDs, secrets and origins for 30 days after deletion (later, or not deleted ->404; at the 25-product limit ->409), and its sites answer again within the same cache time. DELETE /v1/owner/products/:id?permanent=true ->204 removes a deleted product for good (a product that isn't deleted ->404): its environments and origins, and every session, declaration, activity event and install note its sites recorded, in one statement. The prune does the same for products deleted more than 30 days ago. GET /v1/owner/products/:id/environments -> `{environments}`. POST to the same path JSON `{type,name?,origins}` ->201 `{environment,serverSecret}` adds a production, beta, staging or dev environment; a product has one of each type (else ->409). Under /v1/owner/products/:id/environments/:environmentId: GET or PATCH (JSON `{name?,origins?}`; the type is fixed) -> `{environment}`. GET /events?limit=100 -> `{events}` for that environment only. GET /analytics?range=24h|7d|30d&sessionId= -> `{range,from,checkedAt,truncated,overview,sessions}` summarizes that environment's activity received in the period (default 7d), from at most its latest 10,000 events (`truncated` says when more exist), optionally for one session. `overview` counts sessions, sessions per label, page views, signed requests (verified or not), actions per outcome, declarations per choice, and actions and signed requests without a session, all straight from events unique per ID. `sessions` lists up to 100, newest first, each with one `label` (`verified_signer`, `declared_ai`, `suspected_automation`, `declared_person` or `unknown`, in that order of precedence, never human), every signal it carries and its `conflicts`, which are listed, never resolved. GET /activity?limit=100&sessionId=&type= -> `{events}`, that environment's activity events newest first by `receivedAt`, optionally for one session (sessionId must be a UUID) or one event type, else ->400. POST /secret -> `{environment,serverSecret}` rotates its secret: the old one keeps working for 24 hours, and rotating again during that time ->409. DELETE /secret/previous ends the old secret now. A session records which secret signed its binding context and its receipt uses that same secret, so a server that hasn't deployed the new secret keeps working. GET /domains -> `{domains}` lists each origin's hostname, its status (unverified, verified or not_applicable) and the TXT record to publish. POST /domains/verify JSON `{domain}` checks that record; no match ->422, another owner already verified it ->409. Verification never blocks events. Each environment carries `install` `{status:"waiting"|"receiving",loaded:[{origin,firstSeenAt,lastSeenAt}],lastServerReportAt,lastDeclarationAt,checkedAt,issues:[{signal,origin,firstSeenAt,lastSeenAt}]}`, where `checkedAt` is the collector's own time. Only traffic the collector received changes it, so copying a snippet never shows an install as connected: `receiving` needs a session started (`loaded`, by the page script or the widget) from an origin the environment still allows, or a report the collector accepted from the customer's server on /v1/signatures, /v1/signals or /v1/actions. `lastServerReportAt` is the latest such report; a refused secret or invalid report doesn't count. A signature that fails its check still counts, because the server reported it correctly. Issues are refusals from the last 7 days: `origin_refused` (a page on an origin the environment doesn't allow tried to start a session; it clears once that origin is allowed), `secret_refused` (a server request used a secret the site doesn't accept; origin null) and `binding_refused` (the collector couldn't verify a binding context). Requests can claim any origin or secret, so issues say what reached the collector, not who sent it. Every query is scoped to the verified owner; another owner's product or environment ->404, so IDs cannot be probed. Origins are exact, with no wildcards or paths, 1–20 per environment. An account has up to 25 products.
- GET /health -> `{ok:true,version,storage:"postgres"|"memory"}`, where `version` is the package version, such as "0.2.0" (no secrets); production must reject memory store.
- Install activity: the collector notes session starts (`loaded`), declarations and those three refusals per site, at most once a minute per site, signal and origin, and at most 20 origins per site and signal. It stores the signal, origin and first and last times, never visitor details, and a note that fails never fails the request. A session preflight (OPTIONS /v1/sessions) from any HTTPS or local origin is answered, so a browser on an unlisted origin sends the request and its site's owner can see the refusal. The session request itself is still refused with 403 and no CORS header. Preflights for other routes still need an origin some site allows.
- POST /v1/signatures JSON `{siteId, request:{method,url,headers?}, cdn?, sessionId?, accountRef?}` -> `{event}` (a SignatureEvent). Server-to-server only (a request with an Origin header ->403), Authorization:Bearer the site's secret, rate limited per site (600 a window by default). `request.headers` holds lowercase names: `signature`, `signature-input`, `signature-agent` and any other header the signature covers. The collector checks a Web Bot Auth signature (draft-ietf-webbotauth-httpsig-protocol-01, RFC 9421): a member of Signature-Input tagged `web-bot-auth` must cover `@authority` (or `@target-uri`) and its own `"signature-agent";key="<label>"` (the older single-string Signature-Agent with plain `"signature-agent"` is also accepted), with `created`, `expires` and `keyid`. The authority must be one of the site's origins (else `wrong_authority`); `created` may be at most 60 seconds ahead, `expires` must be in the future, and the window at most 24 hours (else `expired`). Signature-Agent must name an allowlisted signer (else `unknown_signer`). Its key directory is `/.well-known/http-message-signatures-directory` at that origin, or the URL itself when it has a path; it is fetched over HTTPS without redirects, cached by Cache-Control for up to a day, retried after five minutes on failure without dropping cached keys, and keys outside their `nbf`/`exp` are ignored (unreachable ->`key_unavailable`). The key is found by its RFC 7638/8037 thumbprint, never by the directory's `kid`, and Ed25519 and RSA-PSS-SHA512 are checked (no matching key or signature ->`bad_signature`; anything unparseable ->`malformed`). The event ID is derived from the signature, so a retried report returns the same event, and the same signature on a different request is recorded as a separate `replayed` event. `cdn` `{verifier:"cloudflare"|"akamai"|"vercel", signer}` records the host CDN's own verdict as `cdn_reported` instead; only use it when the CDN sets the value and strips any copy a client sends. The default allowlist lists ChatGPT agent (`https://chatgpt.com`); no signer is described as supported until a real signed request from it has been verified on the hosted collector. Server helper `reportSignedRequest(request,{apiUrl,siteId,secret,sessionId?,accountRef?,url?,onError?,fetch?})` accepts a Fetch Request or Node IncomingMessage, skips requests without a signature and, unless `includeAssets` is set, asset requests (a `Sec-Fetch-Dest` other than document or iframe, or a static file extension) so one page load counts once, forwards only covered headers, and resolves to `{status:"skipped"|"recorded"|"failed"}` without throwing.
- POST /internal/prune (also GET for authenticated Vercel cron), Bearer PRUNE_SECRET, deletes expired retained data, old rate buckets and refusals older than the retention period, and returns `{removedSessions,removedRateBuckets,removedActivity,removedProducts,more}`. Loads and declarations stay as install history. Retention7days by default; activity events are kept 30 days, after their session has gone. Request handling also opportunistically prunes bounded stale records. No raw visitor IP stored; rate buckets hashed per site+client key, expires quickly.

Sites load from the environments and environment_origins tables: an account has products, a product has environments, and each environment holds its own site ID, secret and origins. Secrets are encrypted at rest with AES-256-GCM and bound to their site ID, minimum32characters. Operator sites have no owner and cannot be reached through the owner API. Anonymous visitor session is site+origin scoped. Customer site servers derive bindingContext from their own active session using createBindingContext; never trust a binding from a browser request. Server helper verifyDeclaration must require expected siteId, origin, secret, actual sessionBinding and currenttime. Unbound anonymous receipts MUST be rejected by this helper. Accepted classification does not authorize action on its own: customer still checks account permissions.

JWT-like HMAC-SHA256 signed contexts/receipts with purpose separation, strict claims and expiry. Bindings opaque server-derived strings, hashed for stored claims. Never put personal data in bindings. Context short-lived (max15min); declaration receipt lifetime no longer than collector session and context where bound. Shared server helpers live src/server/index.ts. Backend can import helpers with additional internal mint/verify exports from src/server/tokens.ts (not public package entry).

## Activity events

Since 0.2.0 (`ActivityEvent` in src/protocol.ts), each session has one timeline that is appended to and never rewritten. Signals from different sources sit side by side even when they disagree, such as a Person answer next to the host's report of an agent-like action, so nothing merges or overrides them.

Every event has `id` (a lowercase UUID chosen by the reporter), `siteId`, `sessionId` (the collector session when the reporter knows it, else null), `origin` (the page's origin for browser events, null for server events), `type`, `source` (`browser` or `server`), `evidence`, `occurredAt` (when the reporter says it happened), `receivedAt` (the collector's time) and `accountRef`. IDs are unique per site. A retry with the same ID and the same content, apart from `receivedAt`, is a duplicate and returns the stored event; the same ID with anything else changed is a conflict (409). Times are ISO 8601 UTC.

- `declaration`: source `browser`, evidence `self_reported`, `choice` and `agent` `{name,provider,purpose}`, each null when unknown. Every accepted declaration becomes one, with the same ID as its legacy event, in the same write.
- `page_view`: source `browser`, evidence `browser_reported`, `path` and `route`. `path` is the route path from `routePath()`: no query or fragment, and segments that look like IDs (all digits, UUIDs, 12 or more hex characters, anything with `@`, or letters mixed with three or more digits in 8 or more characters) become `:id`, at most 512 characters. The collector applies it again, so masking never depends on the browser. `route` is the host's own pattern, such as `/tickets/:id`, for anything masking can't catch. A browser report can come from any client that copies the public site ID.
- `action`: source `server`, evidence `host_reported`, `action` named by the host (lowercase, such as `ticket.update`), an opaque `resourceRef` and `outcome`: `attempted`, `rejected` or `confirmed`, where confirmed means the host's application says it succeeded.

- `signature`: source `server`, evidence `signature_verified` (the collector checked a Web Bot Auth signature against an allowlisted signer's published key), `signature_claimed` (it couldn't; `result` says why) or `cdn_reported` (the host passed on its CDN's verdict, named in `verifier`), with `signer`, `signatureAgent`, `result` (`verified`, `unknown_signer`, `bad_signature`, `expired`, `replayed`, `wrong_authority`, `malformed` or `key_unavailable`) and the masked `path`. A signature identifies the operator only, never the person or account it acts for, and it never blocks or admits anyone. See POST /v1/signatures.

- `signal` (0.5.0): source `browser` (evidence `browser_reported`, with the page's origin) or `server` (evidence `host_reported`), with `signal` (`webdriver`, `headless_browser` or `agent_user_agent`) and a short `detail`. A signal is heuristic evidence: an automated browser isn't necessarily an AI agent, and a user agent naming one is a claim anyone can send. It never makes a session verified or Declared AI; a session whose strongest evidence is a signal is `suspected_automation`, and a Person answer next to one is a conflict.

`accountRef` and `resourceRef` are opaque IDs of 1–128 characters from A–Z, a–z, 0–9 and `_.:-`, so they can't hold names or email addresses. Only the host's server sets `accountRef`; browser input never does. It names the account used, never who delegated an agent to act. Page titles, page text, form contents and raw IP addresses are never collected. Activity events are kept 30 days.

Producers:

- POST /v1/page-views JSON `{views:[{id,path,route?,occurredAt}]}` (1–10) with the session's Authorization and X-Agent-Site headers, like declarations -> `{results:[{id,status}]}`, where status is `recorded`, `duplicate` or `conflict`. The session, origin and siteId come from the authenticated session, never the body, and the body can't carry `accountRef` or any other field. The collector applies `routePath()` to every path itself. `occurredAt` must be within the last day and at most a minute ahead. A revoked or expired session ->401. Rate limited per site and client (600 a window by default).
- POST /v1/actions JSON `{siteId, actions:[{id,action,outcome,occurredAt,resourceRef?,accountRef?,sessionBinding?}]}` (1–50), server-to-server only (an Origin header ->403), Authorization:Bearer the site's secret -> `{results:[{id,status,sessionId}]}`. An action joins a session only through `sessionBinding`, the host's own session binding as used in binding contexts: the collector hashes it and picks the most recent session started with that binding, preferring one still open. A session ID from the request is never accepted, so nothing a browser sent can attribute an action. Rate limited per site (6000 a window by default). Server helper `reportAction({action,outcome,resourceRef?,accountRef?,sessionBinding?,id?,occurredAt?},{apiUrl,siteId,secret,onError?,fetch?})` validates first, retries with the same ID, never throws, and resolves to `{status:"recorded",id,sessionId,duplicate}` only when the collector confirms it, else `{status:"failed",id,error}`.
- POST /v1/browser-signals JSON `{signals:[{id,signal,detail?,occurredAt}]}` (1–10) with the session's headers, like page views -> `{results:[{id,status}]}`. A page may report only `webdriver` or `headless_browser`, from the page script (on by default since 0.6.0) or the widget's opt-in `automationSignals`.
- POST /v1/signals JSON `{siteId, signals:[{id,signal,detail?,occurredAt,sessionBinding?}]}` (1–10), server-to-server with the site's secret like actions, linked to a session the same way -> `{results:[{id,status,sessionId}]}`. Server helper `reportRequestSignals(request,{apiUrl,siteId,secret,sessionBinding?,onError?,fetch?})` reads the request's User-Agent with `userAgentSignals()`: a token an AI agent or crawler publishes for itself (`AGENT_USER_AGENT_TOKENS`, such as ChatGPT-User) gives `agent_user_agent`, and HeadlessChrome gives `headless_browser`. It skips requests with neither, and asset requests, without a network call, retries with the same IDs, and never throws.
- GET /v1/activity?siteId=...&limit=100&sessionId=&type= -> `{events}`, newest first by `receivedAt`. Server-to-server only, Authorization:Bearer the site's secret, like the declaration export.

## Browser SDK

`init(options)` synchronous returns `Widget` with ready:Promise<SessionStatus>, getState(), reset():Promise<SessionStatus>, pageView({route?}):Promise<void>, destroy():void. Options: container:HTMLElement|string; siteId; apiUrl; mode?:optional|required (defaultoptional); gate?:HTMLElement|string; styleUrl? (default apiUrl+/sdk/v{VERSION}/agent-id.css); bindingContext?:string|(()=>Promise<string>); storage?:session|memory (defaultsession); onRecorded?(RecordedDeclaration); onError?(Error); pageViews?:boolean (default true); route?:string (a route pattern such as /tickets/:id); automationSignals?:boolean (default false; reports navigator.webdriver and headless browsers once per page load). getState returns status|null. destroy restores original gate inert state; never submits/clears server record. reset revokes oldtoken and createsnew; cannot falsely indicate reset while revoke failed. Async results after reset/destroy ignored. No auto-answer. Since 0.4.0 the widget records one page view, with the masked `location.pathname` and the configured route, once per page load when its session is ready and again after reset; `pageView()` records one for apps that change pages without reloading. A failed page view retries twice with the same ID, reports to onError and rejects, never resolving without the collector's confirmation. pageViews:false turns it off. The widget collects no titles, page text, query strings, fragments, fingerprints or credentials, and no webdriver or headless flag unless automationSignals is on.

Since 0.6.0, `track(options)` synchronous returns `Tracker` with ready:Promise<void> (resolves once the first page view is confirmed; rejects after reporting to onError), pageView({route?}):Promise<void>, destroy():void (stops recording; never ends the session). It draws nothing and adds no DOM. Options: siteId; apiUrl; storage?:session|memory (default session); route? (for this page load's first view only); navigation?:boolean (default true: wraps history.pushState and replaceState, always calling through and never unwrapping, and listens for popstate, recording a view when location.pathname changes); automationSignals?:boolean (default true: webdriver and headless_browser once per session, marked in sessionStorage so a reload doesn't repeat them); onError?(Error). It uses the widget's storage key for the same API URL, site and origin without a binding context, so the two share one tab session. It reuses a stored, unexpired session without a GET. An event refused with 401, 404 or 410 drops that session, unless another has been stored for the tab meanwhile, and is retried in a new or stored one with the same event ID; other failures retry twice with the same ID like the widget's. `track()` returns the existing tracker for the same API URL and site when its options match, apart from route and onError, and otherwise throws. Script build `agent-id-track.js` IIFE sets window.AgentIdentificationTracker = {track} and reads data-site, data-api (default script origin), data-storage, data-route, data-navigation ("off" turns it off) and data-automation-signals ("off" turns them off). Its failures only dispatch `agent-identification:error` on document, with `detail.message`, and never change the page.

Widget uses ShadowDOM and external stylesheet; retry/error status is outside any supplied gate. Required mode gates only explicitly supplied DOM container using inert until server confirms any choice. Gate cannot contain widget. Without gate use onRecorded callback forhostUI; explain UI-only clearly. Buttons accessible namedlabels; aria-live forstatus/errors; keyboardworks. Keep minimal neutral UI consistent with research wording. No arbitrary HTML injection.

Session storage key includes API URL+site+origin+binding-context identity (do not persist rawcontext). Restore verifies with server before unlocking. Token scoped to anonymous tab session; memory fallback when storage blocked. Binding callbacks support login changes via reset; document reset on logout. Idempotent init on samecontainer; reject conflictingconfiguration instead of duplicating widgets/listeners.

Script build `agent-id.js` IIFE sets window.AgentIdentification. Reads its own script dataset: data-site, data-api(defaultscriptorigin), data-target(optional autoappendcontainer), data-mode, data-gate, data-storage, data-page-views ("off" turns page views off), data-route, data-automation-signals ("on" turns signals on). No secret. PlainHTML<script defer src=... data-site=... data-mode=...>. Script styling separateversioned CSS. ESM package samecore. React `<AgentIdentification ...options>` mounts owncontainer, exposes onRecorded/onError; cleanup on unmount, no server DOM access.
