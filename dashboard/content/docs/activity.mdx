Each session has one timeline. The [page script](/docs/install#the-page-script) starts the session and adds page views, your server adds what visitors did, and declarations and [signed agents](/docs/signed-agents) join the same timeline. Events from different sources sit side by side, even when they disagree, so you can see a visitor who answered Person next to your server's report of something only an agent would do.

## Page views

Page views come from the [page script](/docs/install#the-page-script), which draws nothing. Since SDK 0.6.0 it records a page view when a page loads, and again whenever the path changes without a reload. An install that only reports from your server has none. It sends the path only: no query string or fragment, and parts that look like IDs or email addresses are replaced with `:id`. The collector masks every path again itself.

If your paths hold other personal details, give your own route pattern for that page, such as `/tickets/:id`:

```html
<script
  defer
  src="…/sdk/v0.6.0/agent-id-track.js"
  data-site="YOUR-SITE-ID"
  data-route="/tickets/:id"
></script>
```

An app that changes pages without the History API can record each change itself, with the tracker that `track()` returns:

```ts
await tracker.pageView({ route: "/tickets/:id" });
```

The declaration widget can record page views too, but its snippets leave them to the page script, so a visit isn't counted twice.

## Actions from your server

Your server reports what it did, with a name you choose, an outcome and opaque IDs:

- **attempted:** a visitor tried it.
- **rejected:** your server refused it.
- **confirmed:** your application says it succeeded.

```ts
import { reportAction } from "@parallel-research/agent-identification/server";

await reportAction(
  {
    action: "ticket.update",
    outcome: "confirmed",
    resourceRef: "ticket_7",
    accountRef: "acct_42",
    sessionBinding: currentSession.id,
  },
  {
    apiUrl: "https://parallel-agent-identification.vercel.app",
    siteId: "YOUR-SITE-ID",
    secret: process.env.AGENT_ID_SITE_SECRET!,
  },
);
```

`sessionBinding` is your server's own session ID, the same one you put in [binding contexts](/docs/server-verification). It's how an action joins the visitor's timeline, so nothing the browser sends can attribute an action. `accountRef` and `resourceRef` are your own opaque IDs, never names or email addresses. `accountRef` says which account was used, never who asked an agent to act.

`reportAction()` retries with the same ID, so a retry is recorded once, and it never throws: it resolves to `recorded` only when the collector confirms it.

Any other server can send the same thing as a plain request:

```sh
curl https://parallel-agent-identification.vercel.app/v1/actions \
  -H "Authorization: Bearer $AGENT_ID_SITE_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"siteId":"YOUR-SITE-ID","actions":[{"id":"8d4f…","action":"ticket.update","outcome":"confirmed","occurredAt":"2026-11-02T12:00:00Z"}]}'
```

## Automation signals

Signals are evidence that a visitor is automated, for agents that neither sign nor answer. They never prove an AI agent: an automated browser might be an ordinary test script, and anyone can put an agent's name in a user agent. A session whose strongest evidence is a signal is labelled **Suspected automation**.

- **From the page:** the page script reports whether the browser says it's automated (`navigator.webdriver`) or headless, once per session. Turn it off with `data-automation-signals="off"`. Automation tools such as Playwright and Selenium set `navigator.webdriver`, and so do many agents that drive a browser in the cloud. An agent that works through a person's own browser usually doesn't.
- **From your server:** `reportRequestSignals(request, options)` reads the request's user agent. It reports a token that an AI agent or crawler publishes for itself, such as `ChatGPT-User` or `ClaudeBot`, and headless Chrome. It skips other requests without a network call.

```ts
import { reportRequestSignals } from "@parallel-research/agent-identification/server";

void reportRequestSignals(request, { apiUrl, siteId, secret, sessionBinding });
```

## In the dashboard

Each product has an **Activity** page for one environment at a time, with the last 24 hours, 7 days or 30 days. It counts sessions, page views, signed requests and confirmed actions separately, and a retry is never counted twice.

Sessions come from the page script, or from the declaration widget. A report from your server joins a session only when it carries that session's binding, and the page script's sessions don't have one yet, so your server's signed requests, signals and actions are counted apart from sessions. Signed requests are also listed on your product page under **Signed agents**.

Each session gets one label from the strongest evidence it has, with no score:

- **Verified signer:** a request in it carried a verified [signature](/docs/signed-agents).
- **Declared AI:** the visitor answered AI assistant.
- **Suspected automation:** it showed automation signals.
- **Declared person:** the visitor answered Person.
- **Unknown:** nothing else. Unknown never means a person.

Every signal stays on the session's timeline, with who vouches for it. When signals disagree, such as a Person answer in a session with a verified signature, the session shows **Conflicting signals** instead of picking one. To find your own test session, open the most recent one.

## Exporting

Your server can read a site's activity with its secret:

```sh
curl "https://parallel-agent-identification.vercel.app/v1/activity?siteId=YOUR-SITE-ID&limit=100" \
  -H "Authorization: Bearer $AGENT_ID_SITE_SECRET"
```

Activity is kept for 30 days.
